## 原则

视频质量主要来自：

```text
清楚的观看承诺
+ 持续的局部回报
+ 图片真正承担内容
+ 时间和运动有层级
+ 用户看到真实播放后持续修正
```

不要把质量变成自动分数，也不要把技术检查当成创意验收。

用户是最终判断者，但 Agent 不是被动执行者。Agent 应先进行导演式自评，指出问题、给出原因和推荐修改，再让用户做选择。

### 展示后必须停止

每次成熟阶段预览（Story Flow、Image Animatic、Timed Animatic、Final Preview）展示后，Agent 必须结束当前回复。只有用户在**后续消息**中明确说可以进入指定下一阶段，才可调用下游工具或继续制作。沉默、最初“做视频”的请求、文件存在、CLI 通过、MP4 成功生成或 Agent 自评都不是许可。

这不是审批状态机：不保存 `approved=true`、不维护状态文件、不自动评分；边界存在于真实对话中。

## Preview Readiness Review：Agent 自审先于用户审片

用户负责创意判断；Agent 负责基础可看性和 HyperFrames 合规。自审必须匹配当前 surface：

```text
Story Flow
官方 Storyboard route
→ Visual-Only Pass：隐藏 Inspector，只看每帧具体视觉信息
→ Sequence Pass：连续浏览 Board，检查变化、发展与 Handoff
→ Source-Separation Pass：检查原文、字幕、导演说明与成片画面分离
→ 任一失败则修复并重做三遍
→ 才能展示

Image Animatic / Timed Animatic / Final
完整播放
→ 关键时刻与 Scene boundary 检查
→ P0 blocker 检查
→ HyperFrames 技术工具
→ 修复
→ 同一路径重播
→ 才能展示
```

存在任一与当前成熟阶段相关的 P0 blocker 时，不得请求用户审片。Story Flow 的 blocker 包括：官方 Storyboard URL / route 不可用；Scene / Beat / Frame 顺序或从属与 Attention Spine 明显不一致；关键视觉状态缺失、重复或没有可渲染 `src`；Frame 空白、近似空白、只有标题 / 版式、使用无语义矩形 / 圆点 / 条形占位；需要读 Inspector 才知道发生什么；旁白、字幕或导演说明被烧进画面补足信息；包含 Reveal、累积、对比、状态改变、重构或回收的 Beat 只展示一个泛化结果帧；或 Board 序列无法基本表达人物、问题、过程、转折和回报。Image Animatic 及之后的 blocker 包括：没有实际 HTTP / HTTPS Studio URL 与准确的当前 Composition route；URL 是 `file://` 或直接指向 `.html` 源文件；页面不是官方 Studio surface；Studio route 未实际加载、播放器不能完整播放或加载错误 Composition；该阶段应有的关键 Frame / Beat / Scene 或图片、音频、字幕、字体资源空白或加载失败；非设计性黑边、露底、错误拉伸或严重裁切；运动时露出空白；字幕 / 平台 UI 遮挡关键内容；旧图层残留、多张全屏层无边界叠加、重叠转场、黑帧、空帧、跳帧、多个竞争主运动或大量 magic offsets；或声画、字幕与揭示明显错位。截图、snapshot、实现源文件、资产目录、技术日志或“检查已通过”均不得冒充用户审片表面。

阶段专属要求：Story Flow 必须在官方 Board Overview 为全部关键视觉状态提供按序、视觉具体的低保真 Frames；低保真只降低美术完成度，不降低视觉导演完成度。用户隐藏 Voiceover / Narrative 后仍应基本读懂整组图片叙事；Inspector 只补充原文、Audience Discovery、Visual Event、Handoff 与 Placeholder / Risk。Story Flow 不要求时间播放、临时声音、字幕时间轴或完整动画；Image Animatic 是第一次完整播放，必须具备主要 Beat 的实际画面和最低必要运动；Timed Animatic 必须使用正式声音与 `captions.json` 的真实字幕时间轴；Final 不得保留占位 / 审核标记或明显生成错误。Timed Animatic 及之后，Composition 内临时切字幕而非读取 `captions.json` 属于 P0 blocker。

技术工具通过只是技术信息，不能抵消上述视觉问题。Story Flow 只有在 Agent 实际获得官方 Storyboard surface 的像素级预览并逐卡复查后，才能说“已在 Studio 中确认”；Image Animatic 及之后还必须完整观看对应 Composition。若无法视觉访问，必须报告自审受阻并先解决预览访问，不能猜测画面正确、让用户充当第一轮 QA，或把未经自审的地址作为阶段预览交付。

## 审片不是一次总评

用户若被要求一次同时判断内容、图片、字幕、节奏、声音、转场和风格，反馈往往会变成：

> 好像哪里不对。

因此每次预览明确一个主要审片问题。Story Flow 先隐藏 Inspector 浏览 Board 上的 Frame 序列，再按需打开 Inspector；Image Animatic 及之后可以完整播放多次，但每次关注不同层。

### 不要同时问十个问题

展示后先说：

> 这轮只重点判断两个问题：第一层回报是否太晚，以及第 3 段的图片是否真正证明了“选择成本”。视觉精修和音效暂时不看。

用户仍可以自由反馈其他问题，但主要判断会更清楚。

## 七轮审片法

这些不是七个强制审批阶段，而是七种观看视角。按当前成熟度选择使用。

## 第一轮：注意力审片

### 看什么

- 第一帧是否有具体事件；
- 第一段旁白是否直接进入；
- 第一层回报是否足够早；
- 中段哪里想划走；
- 是否不断获得新东西；
- 开头承诺是否最终兑现。

### 怎样看

不暂停，像真实抖音观看一样完整播放。

### Agent 记录

```text
最强 5 秒：
最弱 5 秒：
第一层回报时刻：
主问题关闭时刻：
最可能划走的位置：
```

这些是导演笔记，不是自动门禁。

## 第二轮：叙事与认知审片

### 看什么

逐段问：

- 进入时观众怎样理解；
- 本段新增了什么；
- 离开时理解如何变化；
- 证据是否足够；
- 段落之间是否因果相连；
- 是否有重复解释；
- 是否仍像同一个人在讲；
- 是否把具体故事压缩成案例摘要，或把人物变成概念载体；
- 原稿的惊讶、挫败、希望、落空和释放是否仍在；
- 互动句是否仍给观众反应的位置；
- 是否为了逻辑清楚而提前说完答案。

### 典型问题

> 第 2 段与第 3 段都在说计划带来负担，但没有新的层次。Development / Revision Mode
> 可以考虑合并，或者让第 3 段负责一个真正不同的原因；Locked Script Mode 则先用不同的图片任务、
> 停留或证据层次保留原文的叙事功能。

## 第三轮：图片叙事审片

### 看什么

- 图片是否证明内容；
- 哪些图只是气氛；
- 一张图是否承担了清楚的观看任务；
- 重大重构是否在画面中成立；
- 图片之间是否有视觉交接；
- 编辑文字是否替图片讲了太多。

### 怎样看

可以：

- 静音观看；
- 忽略编辑文字；
- 逐拍暂停；
- 只看缩略图序列。

### 核心问题

> 如果观众只读字幕而不认真看图片，是否会错过重要证据和关系？

若不会，图片可能太弱。

## 第四轮：时间与节奏审片

### 看什么

- 旁白是否过密；
- 复杂图片是否有阅读时间；
- 关键回报是否缺少停顿；
- 每个 Scene 是否同样快或同样慢；
- 转场是否抢内容；
- 字幕是否频繁闪过；
- 结尾是否被 CTA 挤压。

### 区分四种“慢”

1. **回报慢**：一直铺垫，解决内容结构；
2. **语言慢**：句子冗长，解决旁白；
3. **视觉慢**：图片没有新发现，解决图片节拍；
4. **动作慢**：动画时长过长，解决时间线。

不要一律全局加速。

## 第五轮：HyperFrames 视觉审片

### 看什么

- 英雄帧是否成立；
- 观众第一眼看什么；
- 元素出现顺序是否符合重要性；
- 图片运动是否有语义；
- 同一动画模式是否重复；
- 转场是否表达前后关系；
- 画面是否像网页或 PPT；
- 构图是否适合手机竖屏；
- 字幕是否与图片竞争。

### 观看方式

- 在关键英雄帧暂停；
- 慢速观看复杂段落；
- 在手机尺寸观看；
- 关闭声音检查视觉路径；
- 打开声音检查运动是否与语义同步。

## 第六轮：声音与字幕审片

### 看什么

- 火山 TTS 是否像该系列的说话者；
- Hook、解释、重构和回报是否有语气差异；
- 停顿是否自然，且短行没有因独立 TTS 请求而反复起调、切碎转折或情绪；
- `TTS_REQUEST_UNIT` 是否符合实际听感：默认段落请求保持连续语调，短行请求只用于确认需要的交付节拍；
- 音乐是否支持段落变化；
- 音效是否准确而克制；
- 中文是否按语义而非固定字数断句，且没有在词组、数字、否定或关键宾语中间奇怪断开；
- 字幕是否只在对应意义真正到来时出现，没有提前泄露后半句、答案或下一件事；
- 字幕切换是否对应声音停顿和图片揭示，上一组没有停留到下一事件已经发生；
- Display Text 是否隐藏无意义句法标点，同时保留数字、单位、专有名词和技术表达的必要符号；
- 中文和英文是否属于同一意义单位、默认共享时间区间，英文是否自然而非逐字硬译；英文确实来不及阅读时，只能用同一 `captions.json` 项的 `en_end` 略晚隐藏，不能独立推进信息；
- `captions.json` 是否是 Composition 唯一字幕来源，组内换行没有被当作时间切换；
- 字幕是否可读且不遮挡关键主体。

字幕是基础功能，重点是无摩擦、可靠，不需要成为最抢眼的视觉层。

## 第七轮：完成度与平台审片

### 看什么

- 是否仍有占位图、临时声音或审核标注；
- 图片连续性；
- 生成图错误；
- 品牌资产；
- 来源与隐私；
- 抖音 UI 安全区；
- 片头、片尾和 CTA；
- 音量；
- Studio Final Preview 中的字幕、主体、安全区与画面连续性；
- 手机真实观看效果。

Final Preview 前可运行 lint、inspect 与 validate 修复技术问题。只有用户观看 Final Preview 后在后续消息明确允许导出，才运行最终 render；导出后再检查文件是否与已确认预览一致。

## Collaborative Stage Handoff｜协作式阶段交接

不要只丢一个链接说“请验收”。每次进入成熟阶段前，先用简短说明让用户知道：这一阶段的目标、将做的创作工作、不会做的下游工作，以及完成后需要判断什么。不要汇报普通命令、文件创建、CSS 属性或中间缓存；实现细节由 Agent 承担，影响方向、返工成本或用户判断的创作决定必须透明。

每次展示时，下列信息按当前阶段相关性取用，而不是机械填表或建立审批记录：实际完成工作、导演选择与理由、自审修复、未完成项、用户判断重点、少量方向选项与推荐、确认后的下一步投入和边界。用户确认只存在于后续对话，不写入 `approved=true` 或批准日志。

### Story Flow 专用交接

Story Flow 使用官方 Storyboard surface，不套用 Composition 的播放次数与关键时间点字段：

```text
当前阶段：Story Flow

Storyboard URL / route：
Scene 数量：
Beat / Frame 数量：

这一版完成的节拍设计：
- （Scene 划分、Beat 顺序、原文映射、图片任务与 Handoff）

主要导演选择：
- 选择：
- 原因：
- 代价或备选：（有实质取舍时填写）

Storyboard Readiness Review：
- 检查的 Scene / Beat / Frame 数量：
- Visual-Only Pass：具体主体 / 动作 / 关系 / 证据；空框与泛化图形：
- Sequence Pass：相邻变化、构图变化、Beat / Frame 从属、发展、重构、回报与 Handoff：
- Source-Separation Pass：Voiceover、字幕、导演说明、证据 / 图形层与成片文字分离：
- 已修复的问题：

仍是占位或高风险的 Frame：
-

请先只浏览 Board Overview，不打开 Inspector：
1. 是否能基本看懂人物、问题、过程、转折和回报？
2. 同一 Beat 内的发展，以及相邻 Frame 的变化和 Handoff 是否成立？
3. 哪些 Frame 仍需要改视觉方向？

再打开 Inspector 补充核对对应原文、Audience Discovery 和风险。

确认后 Image Animatic 会做：
- 把已确认 Storyboard Frames 转为第一次完整时间播放；加入低成本素材、估计时长 / 临时声音和粗略 Motion / Reveal / Handoff。

确认后仍不会做：
- 正式 TTS、captions.json、批量最终图、Final 精修或导出。

我先停在 Story Flow，等你浏览 Storyboard 后在下一条消息决定是否继续。
```

### Preview Handoff Test｜交付前最后判定

发送 Image Animatic、Timed Animatic 或 Final 的阶段交接前，Agent 必须能回答：

- 我交付的是哪个 HyperFrames User Review Surface？
- URL 是否是 Studio HTTP / HTTPS URL，而不是文件路径、源文件或独立 HTML？
- route 是否指向当前阶段的正确 Composition？
- 我是否实际打开并完整观看过这个 Studio route？
- 用户点击后能否直接进入同一个审片表面？
- 当前回复是否把 snapshot、截图、源文件或技术检查误称为 Preview？

任一答案不成立，就不能发送 Stage Handoff。停止交付，定位 Studio / route / asset loading / playback 问题，修复后重新完整播放。此检查是交付前判断，不是状态机、批准记录或新的成熟阶段。

阶段审片重点默认是：Story Flow 先在官方 Board Overview 隐藏 Inspector 看画面序列能否直接表达人物、问题、过程、转折、回报和 Handoff，再用 Inspector 补充核对原文、Audience Discovery 与风险；Image Animatic 作为第一次完整播放，看停留、观看动力、图片切换、Reveal / Handoff 和是否像视频而不是幻灯片；Timed Animatic 看正式声音、字幕、声画同步与真实节奏；Final Preview 看整体统一性、镜头感、可读性、声音和发布准备度。用户仍可反馈其他问题，但不要要求其在早期阶段替 Final 做评判。

### 展示多个方案

说明差异和推荐：

```text
A：人物先行，情绪进入更快，但机制感较弱。
B：证据先行，可信度更强，但第一帧较冷。
C：违反直觉对比，最适合抖音，也最容易用图片证明。

我推荐 C 作为开头，同时借用 A 的人物回收。
```

不要把三个方案平铺给用户，却不表达专业判断。

### 技术状态不等于创意状态

技术检查通过时，只能说：

- lint 通过；
- validate 没有发现时间线错误；
- render 命令成功；
- 资源文件存在。

不得因此说：视频已经完成、Storyboard 已通过、图片叙事已经成立、用户可以验收或视觉方向已经确认。创意状态只能由实际 Studio 预览和用户后续消息中的观看反馈确认。

## 问题定位与唯一修复位置

首次生产或重跑单集时，发现问题不要立即扩展架构，也不要在四个文件重复添加规则。先写一条简洁导演问题笔记；它只用于本次诊断，不是状态、审批记录、评分或新工作流。

```text
问题：
发生在哪个阶段：
属于哪一层：
是单集问题还是长期系列问题：
是 Prompt 问题还是 Provider 能力问题：
修复后应该更新哪个唯一权威位置：
```

按问题的根因更新唯一权威位置：

| 问题 | 优先修复位置 |
| --- | --- |
| 内容理解偏了 | `EPISODE.md` / Attention Spine |
| 所有画面都长得一样 | `DESIGN.md` 的 Visual Variety / Image Set Audit |
| 人物或物件不连续 | Episode Visual Anchors / 已确认的 Provider reference 能力 |
| 单张图讲不清内容 | Asset Brief / Prompt |
| 原图好看但进视频失效 | Production Affordances / HyperFrames 实现 |
| 运动不符合媒介 | Motion Affordances / Motion Language |
| 用户太晚才看到方向 | Collaborative Stage Handoff |

如果根因只影响本期，就修本期 Brief、Anchor、Prompt 或 Composition；只有跨多期反复出现且确实改变长期配方时，才更新 `SERIES.md`、`DESIGN.md` 或 `CALIBRATION.md`。不要把 Provider 的能力缺口伪装成 Prompt 问题，也不要为一次单集失误添加新的 Contract、阶段、状态或自动门禁。

## 用户反馈翻译表

用户的感受是有效证据，但通常不是直接实现指令。

| 用户反馈 | 可能的真实问题 | 先检查 | 不要直接做 |
| --- | --- | --- | --- |
| 不够抓人 | 第一帧弱、承诺泛、第一层回报晚 | Hook、图片异常、起句长度 | 全部动画加速 |
| 中间太平 | 没有新证据、局部回报或理解变化 | 注意力主干、段落、图片任务 | 随机加转场 |
| 太慢 | 回报、语言、视觉或动作之一慢 | 分别定位四种慢 | TTS 直接 1.5 倍速 |
| 太快 | 信息密度、字幕、图片阅读或转场过快 | 复杂画面、句长、停顿 | 全局减速 |
| 不高级 | 视觉过载、AI 图、字体、转场炫技、节奏无层级 | 具体画面和运动 | 黑金配色 |
| 像 PPT | 标题页结构、图片是背景、一次性出现 | 图片内揭示、空间层级、衔接 | 只换模板 |
| 图片不对 | 题材、证据、构图、情绪或连续性不对 | 图片任务和失败条件 | 同 Prompt 无限重抽 |
| 图片很漂亮但空 | 没有可见证据或关系 | 图片角色、图片证明 | 再加滤镜 |
| 文字太多 | 编辑文字重复旁白或图片弱 | 删除编辑文字、增强图片 | 缩小文字塞更多 |
| 字幕挡画面 | 构图未预留、安全区错误 | 图片裁切、运动终点、字幕位置 | 把字幕缩很小 |
| 字幕读着别扭或抢戏 | 按标点/字数机械切分、提前泄露或没有跟随图片推进 | 语义组、实际声音时间、图片节拍和 Display Text 清理 | 改写 `SCRIPT.md` 或把字幕缩得更小 |
| 动效太花 | 动作无语义、转场过多 | 主运动、转场系统 | 只降低透明度 |
| 动效太单调 | 所有图同一种运动、速度无对比 | 场景任务、速度和静止 | 每镜加新特效 |
| 声音没力量 | 文案起句、Voice、停顿或语速 | 先听单段 | 全片加音量 |
| 结尾没感觉 | 回报不完整、缺回收、CTA 抢结尾 | 最终回报和开头图 | 加更大 CTA |
| 没感情、像朗读文章 | 讲述立场消失、事件被摘要、情绪高低被压平 | 讲述者、事件链、情绪变化与图片停留 | 只给 TTS 加情绪 |
| 没人味 | 人物动作被替换成概念术语、互动关系消失 | 具体行为、物件、人物与观众关系 | 加一句“你知道吗” |
| 故事不抓人 | 好奇被提前回答、事件链被压缩 | 局部问题、回报顺序与期待 | 无端加强 Hook 或特效 |
| 太像商业分析 | 机制解释压过人物经历和观众发现过程 | 人物处境、互动、情绪与可见事件 | 把人物再摘要成结论 |
| 画面不像这个系列 | Narrative Mode 不清、Reality Level 漂移，或创作自由没有服务意义锚点 | Narrative Contract、图片角色、旁白措辞与关键 Scene | 只换色调或加“更真实”的滤镜 |

## 修改正确层级

先确认当前模式。Locked Script Mode 可以诊断任何层级，但文字、观点、Hook 和回报顺序仍属于锁定源文本；发现风险时报告给用户，不借“内容层”或“注意力层”绕过它。

### 内容层

症状：价值弱、事实不足、主问题不值得看。

- **Locked Script Mode**：只报告作者观点、事实或最终意义的风险；用证据图片、语境和导演笔记帮助理解，不改变选题、角度、证据主张或原文最终回报。
- **Development / Revision Mode**：可以修改选题、角度、证据和最终回报；Revision 仍只在用户许可范围内进行。

### 注意力层

症状：开头弱、中段平、答案拖延、反转不可信。

- **Locked Script Mode**：保留原文 Hook、问题与回报顺序；修改第一帧、视觉揭示、图片关系、停留、声音进入和场景交接。
- **Development / Revision Mode**：可以修改 Hook、回报顺序、证据位置和认知变化；Revision 仍只在用户许可范围内进行。

### 旁白层

症状：冗长、抽象、重复、难图片化、TTS 不自然。

- **Locked Script Mode**：不修改文字；调整图片、声音分段、短行节奏、停留、目标时长和场景关系。
- **Development / Revision Mode**：可以修改句子、顺序、案例、停顿和用词；Revision 仍只在用户许可范围内进行。

### 叙事契约层

症状：观众不清楚自己进入的是纪录、知识故事、电影叙事还是概念世界；综合人物、象征或幻想元素让主题变弱；旁白承诺与画面世界互相冲突。

- **Locked Script Mode**：选择不误导原文的图片角色与关键 Scene，报告原文和系列契约的冲突；不重写叙事措辞或意义。
- **Development / Revision Mode**：回到 `SERIES.md` 的 Narrative Mode、Reality Level、Story License 与 Meaning Anchor，调整叙事措辞、图片角色和关键 Scene 的体验，而不是增加真实性评分或披露门。

### 图片任务层

症状：图片相关但不证明、视觉重复、重构不成立。

两种模式都可以修改图片角色、可见证据、构图和场景关系；Locked Script Mode 优先在这里解决问题。

### HyperFrames 导演层

症状：焦点混乱、运动无意义、转场不连、像 PPT。

两种模式都可以修改英雄帧、观看顺序、GSAP、Scene 划分和转场。

### 资产层

症状：生成图错误、人物不一致、分辨率不足、声音不对。

两种模式都可以修改 Prompt、参考图、选图、Voice 和重新生成。

### 技术层

症状：溢出、路径错误、渲染失败、字幕不隐藏。

两种模式都可以修改 HTML、CSS、时间线、媒体和 CLI 报告。

先找到层级，再动手。不要用下游精修掩盖上游问题，也不要用上游“优化”覆盖 Locked Script Mode 的源文本。

## 怎样主动提出改进

Agent 应具备导演立场，但不把偏好伪装成客观真理。

### 好的建议包含

1. **观察**：具体发生了什么；
2. **原因**：为什么影响观看；
3. **建议**：优先修改什么；
4. **替代方案**：必要时给第二选择；
5. **权衡**：各方案会牺牲什么。

示例：

> 第 12–19 秒连续解释了“完成感”和“奖励”，但图片只停留在同一张计划表，认知已经推进，视觉没有推进。  
> 我建议让完成标记依次亮起，再切到仍为零的任务进度，这样图片能证明“奖励先于工作”。  
> 若这是 Locked Script Mode，我会保留第二句，并用短暂停留和下一拍的结果图承接它；若用户允许 Revision Mode，备选才是删掉第二句解释，把这个机制留到后面。

### 建议优先级

优先提出能明显改善：

- 最终回报；
- 第一层回报；
- 图片证明；
- 中段平坦；
- 结尾回收。

不要把大量精力放在用户尚未关注的细微装饰上。

### 保留不确定性

可以说：

> 我倾向 A，因为它让图片承担更多证据，但用户是否觉得第一帧过冷，需要实际观看判断。

这比假装存在唯一正确答案更可信。

## 怎样控制迭代范围

### 每轮设一个主要问题

例如：

- 本轮只修 Hook；
- 本轮只修第 3 段图片表达；
- 本轮只校准正式声音后的时间；
- 本轮只处理风格统一。

### 改动影响大时完整回看

修改以下内容后，应从头完整播放：

- Hook；
- 最终回报；
- 段落顺序；
- 正式 TTS；
- 关键图片；
- 核心转场；
- 结尾。

### 小修改局部回看

- 字幕换行；
- 单个裁切；
- 一处 easing；
- 小音量；
- 一处标注。

完成后仍做一次最终全片播放。

### 防止版本分叉

用户选定方案后，将获胜内容折回真实项目。不要长期维护 A/B/C 三套最终视频。

### 记录有效决定

在 `EPISODE.md` 或 `STORYBOARD.md` 简洁记录：

```text
保留 C 的第一帧，因为异常最具体。
使用 A 的人物回收，因为结尾更有情绪。
删除“选择成本”大字，图片已足够清楚。
```

不需要状态机或审批证据。

## 不同阶段的质量重点

### 系列初始化

质量来自：

- 系列价值清楚；
- 方向有辨识度；
- Series Style Calibration 测试可复用的图片、声音与运动身份，不测试某期内容；
- 用户看过声音、图片和运动；
- `DESIGN.md` 可执行。

### Story Flow

质量来自官方 Storyboard surface 上的设计完整性：

- Scene / Beat / Frame 顺序与从属匹配 Attention Spine；
- 每个 Frame 有具体主体、动作 / 状态 / 关系、事实 / 证据、相邻变化和 Handoff；
- Reveal、累积、对比、状态改变、重构与回收通过足够的关键 Frame 展示，不被压成泛化结果卡；
- Board Overview 隐藏 Inspector 后仍能基本读懂人物、问题、过程、转折与回报；
- 相邻 Frame 不是重复构图，变化和 Handoff 可比较；
- Voiceover、字幕、导演说明、内部工作信息与 Frame Canvas 清楚分离；
- Inspector 保持简洁，只补充原文、Audience Discovery、Visual Event、Handoff 与 Placeholder / Risk。

不要追求完整时间播放、最终图片、正式声音或动画流畅度；但不得把“低保真”误解为视觉设计未完成。

### Image Animatic

质量来自：

- 图片证明内容；
- 观看顺序清楚；
- 镜头关系成立；
- 字幕安全；
- 画面不重复。

### Timed Animatic

质量来自：

- 正式声音节奏；
- 字幕阅读；
- 图片停留；
- 快慢对比；
- 回报停顿。

### Final

质量来自：

- 最终资产；
- 连续性；
- 精细运动；
- 声音混合；
- 平台安全；
- 技术可靠；
- 用户完整观看后的认可。

## 系列一致性与单集新鲜度

系列一致性不等于每期套同一模板。

### 应保持稳定

- 系列价值和语气；
- 图片质感；
- 字幕层级；
- 字体和颜色角色；
- 主运动气质；
- 主转场家族；
- 编辑文字边界；
- 旁白角色。

### 应根据内容变化

- Hook 结构；
- 具体场景；
- 人物和物件；
- 图片节拍；
- 证据形式；
- 场景数量；
- 强调转场；
- 音乐能量；
- 结尾回收。

### 更新系列基线的时机

当多期反复出现同一改进，或 Provider、图片语言、长期人物、字幕系统发生明显变化时：

1. 提出系列级建议；
2. 做一次 Series Style Calibration；
3. 用户观看；
4. 更新 `SERIES.md` 和 `DESIGN.md`。

不要让单期临时处理悄悄改变所有未来视频。

## 常见失败模式

### 1. 只问“满意吗”

用户难以给具体反馈。应说明本轮问题和 Agent 判断。

### 2. 用户反馈被逐字执行

“快一点”直接全局加速，而不分析原因。

### 3. Agent 过度防御方案

用户不喜欢时解释为什么设计正确，而不是学习。

### 4. Agent 没有立场

只给选项，不给推荐和权衡。

### 5. 一轮改太多

无法知道哪项改动真正有效。

### 6. 下游修上游

用滤镜、转场和动画修复价值弱、文案长或图片空。

### 7. 原型过度精修

方向未定就投入最终图片和音效。

### 8. 技术警告被当成创意评分

inspect 报告用于修布局，不决定视频是否吸引人。

### 9. 只在电脑看

不检查手机竖屏、字幕和抖音 UI。

### 10. 系列一致性变成复制

每期相同开头、构图和转场，内容失去新鲜度。

## Final Preview 前最后观看

在 Studio 中完成四次完整观看后，展示 Final Preview 并停止；只有用户在后续消息明确允许导出，才能生成最终文件：

### 1. 正常观看

不暂停，判断是否愿意看完。

### 2. 静音观看

检查图片、字幕和视觉结构。

### 3. 只听声音

检查旁白、音乐、音效和逻辑。

### 4. 手机观看

检查真实尺寸、抖音 UI、安全区、字幕和细节。

最后确认：

- 开头没有空白和栏目铺垫；
- 第一层回报明确；
- 核心证据可见；
- 最终回报完整；
- 图片不是装饰；
- 编辑文字克制；
- 双语字幕可靠：按语义组推进、不提前泄露、不过度显示句法标点，且数字与专有名词完整；
- 没有占位或审核标注；
- 声音平衡；
- Studio Final Preview 是用户实际观看的同一路径和同一资源。

导出获准并完成后，才额外确认渲染结果与已确认的 Studio Final Preview 一致；这项导出后检查不能反过来替代 Final Preview 或用户的导出许可。
