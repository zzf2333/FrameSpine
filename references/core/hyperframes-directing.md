# HyperFrames 导演手册：最大化使用制作底座

## 这份 reference 解决什么问题

本 Skill 不建立一套平行的 HTML 编译器，也不把所有视频套进统一模板。

Agent 直接使用 HyperFrames 全套 Skills，把内容、图片、声音和用户反馈制作成真实 composition。

这份 reference 负责连接：

```text
注意力与图片导演意图
        ↓
HyperFrames Scene、布局、媒体层和时间线
        ↓
Studio 可播放预览
        ↓
用户反馈与修改
        ↓
最终渲染
```

## 什么时候必须读取

- 制作系列 calibration composition。
- 创建单集 Story Flow、Image Animatic 或 Final。
- 不知道应该保持同一 Scene 还是切换 Scene。
- 图片运动重复、像 PPT 或转场炫技。
- 需要选择应读取的 HyperFrames Skill。
- 需要把用户反馈翻译成具体 GSAP 和构图修改。

# 一、能力路由：什么任务读取什么 Skill

不要一次加载所有资料。根据当前任务读取。

| 当前任务 | 必须或建议读取的 HyperFrames 能力 |
| --- | --- |
| 建立项目、composition、媒体和时间线 | `hyperframes` |
| 初始化、转写、检查、预览和渲染 | `hyperframes-cli` |
| 图片推拉、分层、遮罩、图形和精细时间线 | `gsap` |
| 视觉身份、字体和信息层级 | HyperFrames typography reference |
| 运动速度、缓动、编排和动静对比 | HyperFrames motion principles |
| Scene 关系和转场 | HyperFrames transitions reference |
| 中英文字幕实现 | HyperFrames captions reference |
| 证据框、划线、圈选和关键词强调 | HyperFrames CSS patterns reference |
| 音乐真正参与画面节奏 | HyperFrames audio-reactive reference |
| 数据、数字或机制图 | HyperFrames data / infographic references（如项目中可用） |

原则：

> 先由内容决定需要什么能力，再调用能力；不要为了“榨干工具”把所有效果都塞进一条视频。

最大化使用 HyperFrames 的含义是：

- 它尽早参与原型；
- 它承担真实构图和时间；
- 它让图片在时间中表达；
- 它为用户提供可播放反馈面；
- 它在最终阶段提供完整制作与技术检查。

# 二、先建立视觉身份

在任何正式 composition 之前，读取系列 `SERIES.md` 中的 Narrative Contract，再完善 `DESIGN.md`。

`DESIGN.md` 必须把用户系列方向、Narrative Contract 和 calibration 反馈编译为可执行的视觉身份，包括：

- Style Prompt；
- 图片世界与质感，以及它对应的 Narrative Mode；
- 色彩角色；
- 字体和排版；
- 竖屏构图；
- 图片运动语言；
- 转场语言；
- 字幕基本样式；
- 编辑文字；
- 声音节奏提示；
- What NOT to Do。

不要使用通用蓝色、默认字体和随手选择的渐变。

HyperFrames 自身要求先有视觉身份，再开始 composition；本 Skill 的系列初始化负责让这份视觉身份来自用户的目标与叙事契约，而不是模板。

# 三、一个单集只维护一个持续演进的 HyperFrames 项目

默认结构：

```text
episode/
├── EPISODE.md
├── STORYBOARD.md
├── narration.txt
├── assets/
└── video/
    ├── index.html
    ├── compositions/
    └── ...
```

同一个 `video/` 项目依次成熟：

```text
Hook / Story Flow
→ Image Animatic
→ Timed Animatic
→ Final Composition
```

不要为每个阶段重新生成五套完全独立工程。

需要保留用户审阅历史时，可以：

- 导出短 MP4；
- 保存关键帧截图；
- 复制一个明确命名的 composition；
- 使用版本控制。

不要建立审批数据库。

# 四、Scene、图片节拍与 sub-composition

## 1. Scene 是视觉空间，不是旁白句子

同一空间或图像中连续揭示多个信息时，保持同一 Scene。

适合保持同一 Scene：

- 人物与环境逐步建立；
- 一张证据不断放大；
- 同一构图中变量替换；
- 多个因素累积；
- 具体场景逐步转成机制图。

适合切 Scene：

- 空间、时间或观看问题发生变化；
- 从人物进入证据；
- 从结果回溯原因；
- 核心 Reframe 需要视觉重置；
- 进入结尾回收。

## 2. 图片节拍可以存在于 Scene 内

一个 Scene 的 GSAP timeline 可以包含多个图片节拍：

```text
0.2s 人物进入
1.0s 通知亮起
1.8s 窗口增加
2.6s 镜头拉远
3.5s 关系线形成
```

这样比每句话切一张图更有空间连续性。

## 3. sub-composition 的使用

适合拆为 sub-composition：

- 可复用双语字幕组件；
- 重复出现的片头和片尾；
- 复杂证据卡；
- 机制图；
- 人物卡片；
- Hook 候选；
- 有独立内部时间线的复杂 Scene。

不需要把每个简单 Scene 都拆成文件。

## 4. 根 composition 的职责

- 安排全片 Scene；
- 管理音频；
- 管理整体时长；
- 管理 Scene 间转场；
- 组合可复用组件。

# 五、先做英雄帧，再做动画

## 1. 英雄帧定义

每个 Scene 先确定：

> 信息最完整、观看顺序最清楚、关键元素都处于正确位置的静态时刻。

先完成静态 HTML 和 CSS：

- 图片裁切；
- 主体位置；
- 字幕安全区；
- 编辑文字；
- 图形层；
- 背景和前景；
- z-index；
- 竖屏填充。

再用 `gsap.from()` 设计进入，用 Scene 内变化设计发展。

## 2. 为什么重要

如果先把所有东西放在屏幕外，再猜测动画终点，容易出现：

- 主体和字幕重叠；
- 画面空；
- 多个焦点；
- 推近后裁坏；
- 证据区域不可读；
- Scene 最完整时反而混乱。

## 3. 图片 Scene 的静态层级

常见层级：

```text
背景图 / 环境层
主体图层
前景遮挡或纹理
可控证据 / 图形层
编辑文字（如需要）
双语字幕
```

图层不是越多越好。每一层必须帮助观看。

# 六、图片舞台设计

## 1. 使用 wrapper 控制裁切和运动

不要直接动画 video / image 的布局尺寸。使用图片容器：

```text
.scene-image-frame
  └── img
```

容器负责：

- overflow；
- border radius；
- clip-path；
- 屏幕位置；
- z-index。

图片本身或内部层负责：

- scale；
- x / y；
- rotation；
- filter；
- opacity。

## 2. 运动起点、英雄帧、终点

对每张图明确三个状态：

```text
开始看见什么
最完整时看见什么
离开前把什么交给下一镜
```

## 3. 图片分层

有条件时可将图片拆为：

- 背景；
- 人物；
- 前景物件；
- 可控界面；
- 光线和纹理。

用于：

- 视差；
- 逐层揭示；
- 聚焦；
- 环境变量替换；
- 让图形从场景中自然出现。

不要为了视差而粗糙抠图。错误边缘会降低完成度。

# 七、GSAP 导演原则

## 1. 动画是语义，不是装饰

每个 Tween 回答：

- 它引导观众看哪里？
- 它揭示什么新信息？
- 它表达重量、速度还是关系？
- 它怎样进入下一拍？

无法回答时，删除或简化。

## 2. 缓动是情绪

- `expo.out`：直接、自信、强势进入；
- `power3.out`：明确、现代；
- `sine.inOut`：平静、连续；
- `back.out(...)`：有弹性、强调；
- `elastic`：高玩味，谨慎使用。

不要所有 Tween 都用相同 Ease。

## 3. 速度表达重量

- 0.15–0.3s：紧迫、冲击、快速证据；
- 0.3–0.5s：常规解释和专业节奏；
- 0.5–0.8s：重要、克制、情绪；
- 0.8s 以上：需要明确理由，如长距离视线移动或情绪停顿。

## 4. 动画先后即视觉层级

最先运动的元素会被认为最重要。

按内容重要性编排，不按 DOM 顺序。

## 5. Build / Breathe / Resolve

一个 Scene 可以理解为：

```text
Build：信息进入和建立
Breathe：画面可读，最多一个持续运动
Resolve：关键落点或转场接管
```

不要把所有动画都塞在前 20%，然后长时间没有任何变化。

也不要持续不停地动。

## 6. 避免重复运动

一条视频中主动变化：

- 推近；
- 拉远；
- 横移；
- 前景移动；
- 局部遮罩；
- 对比替换；
- 图层累积；
- 静止。

但变化来自内容，不是为了覆盖清单。

# 八、Scene 转场

转场告诉观众前后关系。

## 1. 先说语义，再选效果

```text
这仍是同一问题
这是下一层证据
这里发生认知转折
现在从人物进入机制
这是核心回报
这里开始收束
```

## 2. 系列转场系统

一个系列通常确定：

- 一个主转场，占多数 Scene 变化；
- 1–2 个强调转场；
- 核心回报可使用最有辨识度的一次；
- 结尾使用更简单的收束。

不要每镜使用不同效果。

## 3. CSS 与 Shader

CSS 适合：

- 推移；
- 遮罩；
- 分屏；
- 简洁擦除；
- 轻量模糊和交叉淡化。

Shader 适合：

- 核心形态变化；
- 强烈空间扭曲；
- 视觉世界转换；
- 系列确实需要高完成度的像素级过渡。

不要因为 Shader 可用就默认使用。它增加制作与调试成本。

## 4. Transition Handoff

最强转场通常由 Scene 内已经存在的元素触发：

- 一个物体被放大；
- 一条线穿过边界；
- 相同主体位置替换；
- 前景遮挡整个画面；
- 光线过曝；
- 轮廓匹配。

转场不是 Scene 结束后另加的效果，而是前后镜头共同设计。

# 九、中英文字幕的 HyperFrames 实现

字幕是基础功能，创作重点不在这里，但必须稳定。

## 1. 一个语义组，两种语言

```text
中文主层
英文副层
```

共享时间区间，分别换行和测量。

## 2. 字幕布局

- 提前在图片设计中留安全区；
- 一次只显示一个字幕组；
- 中文更强，英文更弱；
- 使用 `fitTextFontSize` 或文本测量避免溢出；
- 每组结束后确定性隐藏；
- 不覆盖关键人物、物件和证据。

## 3. 动画

字幕动画不应抢图片：

- 轻微进入；
- 必要的词级强调；
- 关键字适度颜色或尺度变化；
- 避免每组不同花式。

字幕实现细节见技术附录与 HyperFrames captions reference。

# 十、编辑文字、证据标记和 CSS patterns

字幕之外的文字非常少。

适合使用 HyperFrames CSS patterns 的场景：

- 圈出证据；
- 划掉旧解释；
- 高亮一个关键短语；
- 在核心 Reframe 命名概念；
- 标记重要数字。

使用原则：

- 图片已经成立；
- 标记只帮助读图；
- 一次使用一个主要强调方式；
- 不对每个字幕词使用装饰；
- 不把视频变成手帐风，除非系列就是这种语言。

# 十一、声音、音乐和音效

## 1. 中文旁白是主要声音叙事

正式 TTS 进入后重新导演时间线。

## 2. 音乐

音乐负责：

- 情绪底色；
- 段落推进；
- 核心回报的重量；
- 结尾收束。

不要让音乐一直高能。注意力来自内容，不是鼓点。

## 3. 音效

适合：

- 证据出现；
- 物体落位；
- 页面、按钮或账单；
- 核心转折；
- 视觉交接。

避免每个元素都配音效。

## 4. Audio Reactive

只有音乐真的参与视觉节奏时使用。

内容决定视觉形态，音频只调节强度和时间。

不要使用通用频谱、彩虹粒子和毫无内容关系的节拍脉冲。

# 十二、制作阶段怎样使用 HyperFrames

## A. 系列 Calibration

目标：测试系列生产语言。

必须真实展示：

- Hook；
- 图片叙事；
- 一次 Reframe；
- 双语字幕；
- 声音；
- 主转场；
- 视觉回收。

不做纯设计组件演示。

## B. Hook Lab

目标：比较观看入口。

使用：

- 2–3 个短 Scene 或 sub-composition；
- 相同系列视觉和字幕；
- 不同第一帧与注意力策略；
- 3–6 秒即可。

## C. Story Flow

目标：看故事、回报和段落。

允许：

- 占位图；
- 简化画面；
- 临时声音。

但必须有真实：

- 图片观看顺序；
- Scene 变化；
- 转场；
- 大致节奏。

## D. Image Animatic

目标：看图片任务和镜头导演。

加入：

- 接近真实图片数量；
- 真实裁切；
- 图片运动；
- 交接；
- 字幕安全区。

## E. Timed Animatic

目标：使用正式 TTS 决定真实节奏。

加入：

- 正式旁白；
- 实际字幕时间；
- 真实停顿；
- 重新调整图片节拍。

## F. Final

目标：提高完成度，不重新设计内容。

加入：

- 最终图片；
- 精细 GSAP；
- 正式转场；
- 音乐、音效；
- 片头片尾；
- 技术检查。

# 十三、图片主导视频的七种常用 Scene Recipe

这些是起点，不是固定模板。

## Recipe 1：证据放大 Evidence Zoom

### 用途

从文件、截图、账单或产品整体进入关键细节。

### 布局

- 全屏证据图；
- 可控高亮层；
- 双语字幕在安全区；
- 关键细节有放大余量。

### 时间线

```text
整体进入
→ 轻微停留建立可信度
→ 推近关键区域
→ 背景降权 / 证据框出现
→ 从该区域交给下一 Scene
```

### 读取

HyperFrames、GSAP、CSS patterns、typography。

### 风险

- 一开始就放大，观众不知道整体是什么；
- 文字太小；
- 高亮元素过多。

## Recipe 2：同一主体，变量替换

### 用途

证明结果来自环境、产品或选择差异。

### 布局

- 主体位置固定；
- 背景和关键变量分层；
- 前后构图匹配。

### 时间线

```text
状态 A 建立
→ 关键变量突出
→ 遮罩或匹配转场替换为 B
→ 结果变化出现
```

### 读取

GSAP、transitions、motion principles。

### 风险

- 主体不一致；
- 同时改变太多变量；
- 结果不明显。

## Recipe 3：环境分层揭示

### 用途

从人物表面问题转向环境机制。

### 布局

- 人物主体；
- 环境层；
- 干扰物层；
- 图形关系层。

### 时间线

```text
人物和任务
→ 通知 / 物件依次出现
→ 镜头拉远
→ 关系形成
→ 短暂 Reframe
```

### 读取

HyperFrames、GSAP、motion principles。

### 风险

- 元素过多；
- 全部同时出现；
- 关系线抢画面。

## Recipe 4：多图累积

### 用途

多个小因素、账单、证据或后果逐步形成大结果。

### 布局

- 固定主锚点；
- 图像卡片或裁切层；
- 清楚的加入方向。

### 时间线

```text
第一项建立
→ 后续项以不同但一致的节奏加入
→ 空间被占满或形成系统
→ 关键结果落位
```

### 读取

GSAP stagger、motion principles、typography（数字时）。

### 风险

- 等距网格看起来像模板；
- 每项权重相同；
- 画面没有最终结构。

## Recipe 5：视觉接力 Match Handoff

### 用途

在 Scene 间保持连续，避免随机切图。

### 布局

前后 Scene 共享：

- 物体；
- 方向；
- 轮廓；
- 色块；
- 主体位置。

### 时间线

前 Scene 内把共享元素带到转场中心，转场接管，后 Scene 从相同状态继续。

### 读取

transitions、GSAP。

### 风险

- 只匹配颜色，没有语义；
- 共享元素过小；
- 转场后观众仍需重新寻找焦点。

## Recipe 6：机制构建

### 用途

把抽象关系逐步做出来。

### 布局

- 从真实场景或具体物件开始；
- 关系线、标签和节点可控；
- 保留图片主导。

### 时间线

```text
具体对象出现
→ 对象之间关系显现
→ 关键节点强调
→ 机制命名
→ 回到现实结果
```

### 读取

GSAP、CSS patterns、typography、可能的数据 reference。

### 风险

- 一上来就是信息图；
- 标签过多；
- 图形和图片像两个世界。

## Recipe 7：开头回收 Callback

### 用途

结尾重新解释开头。

### 布局

重用开头资产、构图或主体位置，但改变关键变量或观看含义。

### 时间线

```text
回到熟悉画面
→ 展示已经变化的关键点
→ 旁白给出最终回报
→ 简洁收束
```

### 读取

HyperFrames、transitions、motion principles。

### 风险

- 只是重复开头；
- 没有实际变化；
- CTA 抢在回报前。

# 十四、HyperFrames Studio 中的用户共创

## 1. 给用户可判断的 URL 或导出

展示 Studio 项目，而不是让用户读 HTML。

## 2. 每次预览明确审片问题

例如：

> 这版请重点看 0–5 秒的 Hook 和 17–24 秒的机制转折。第一段我做了两种不同速度；第二段用一张图连续揭示，避免随机换图。

## 3. 根据反馈直接改当前 composition

用户说“第二段太慢”时，先诊断内容、图片和时间，再修改。

不要先更新状态文件。

记录：


比“全片再优化一下”更有效。

# 十五、技术检查的使用时机

## 迭代中

```bash
npx hyperframes lint
npx hyperframes inspect --at <关键英雄帧时间>
npx hyperframes preview
```

`inspect` 重点检查：

- Hook 英雄帧；
- 证据放大；
- 核心 Reframe；
- 最终回收；
- 双语字幕最长组。

## Final 前

```bash
npx hyperframes lint
npx hyperframes validate
npx hyperframes inspect --samples 15
# 需要时运行 animation map
npx hyperframes preview
npx hyperframes render --quality high --output final.mp4
```

## 工具发现的问题

- 溢出；
- 对比度；
- 媒体路径；
- Scene 时长；
- 轨道冲突；
- 字幕残留；
- 渲染错误。

工具不判断：

- Hook 是否有吸引力；
- 图片是否有感染力；
- 用户是否喜欢；
- 结尾是否有价值。

# 十六、常见 HyperFrames 失败模式

## 1. 每个 Scene 都是标题 + 图片

结果像 PPT。

修正：图片内部必须有发展和新增信息。

## 2. 所有图片都慢推近

结果没有导演意图。

修正：根据聚焦、揭示、替换、累积和交接选择运动。

## 3. 所有元素同方向入场

结果模板化。

修正：按元素角色和空间来源设计。

## 4. 转场各不相同

结果像特效展示。

修正：系列使用主转场与少量强调转场。

## 5. Shader 过度使用

结果抢内容且调试困难。

修正：只在视觉世界转换或核心回报使用。

## 6. 图片、字幕和编辑文字同时竞争

结果手机上无法阅读。

修正：图片主体第一、字幕稳定、编辑文字能删就删。

## 7. 画面一直动

结果没有重量。

修正：使用 Breathe 和 Hold。

## 8. 依赖浏览器随机状态

结果不可确定渲染。

修正：遵守 HyperFrames 确定性时间线与媒体合同。

## 9. 最终阶段重写 composition

结果用户批准的结构消失。

修正：同一项目渐进替换资产和精修。

# 十七、完成标准

HyperFrames 项目已经准备好交付，当：

- 视觉身份来自系列基线；
- 每个 Scene 英雄帧清楚；
- 图片运动有语义；
- Scene 切换有关系；
- Hook、证据、Reframe 和回收获得最合适的 HyperFrames 能力；
- 双语字幕稳定但不抢画面；
- 用户看过完整预览并完成最后修改；
- lint、inspect、validate 没有未处理的实现问题；
- 最终 render 与 Studio 预览一致。

# 十八、实现时继承 HyperFrames 的技术合同

这些是制作底座的技术规则，不是创意门禁：

- composition 使用明确的 `data-composition-id`、尺寸、时长和轨道；
- GSAP timeline 使用 `{ paused: true }` 并注册到 `window.__timelines`；
- 先完成静态英雄帧，再用 `gsap.from()` 设计元素进入；
- 多 Scene composition 必须有语义明确的转场；
- 每个 Scene 的可见元素都应有入场，不突然完整出现；
- 除最后 Scene 外，不在转场前先把内容退场或淡出，转场负责视觉交接；
- 时间线保持确定性，不使用 `Math.random()`、`Date.now()` 或异步构建；
- 不使用无限 `repeat: -1`；
- 视频素材静音，音频使用独立轨道；
- 不手动调用媒体的 play / pause / seek，交给 HyperFrames；
- 字幕组结束后确定性隐藏；
- 最终以当前 HyperFrames 主 Skill 与官方 references 为准。

出现技术冲突时，回到 HyperFrames Skills 解决，不在本 Skill 中发明平行规则。
